# Windows 更新链路

参考 [android-app-update skill](https://github.com/daxiaamu/update-by-github-skill/blob/main/SKILL.md) 的共享会话、版本/渠道、策略防回滚、不可变清单、固定弹窗和重新校验流程。Windows 目标差异如下：

- APK 安装换为独立 WinExe 辅助进程更新整个便携目录，使用 PE 程序身份、包内文件清单及可选 Authenticode 连续性校验。
- 按用户明确选择，GitHub 官方源为主；镜像完整校验后作备用，不采用 Android skill 中必须凑齐 5 个第三方镜像的发布门槛。
- 元数据保留 7 个 HTTPS 入口。未配置应用层签名时，不用镜像多数投票产生新信任；只接受官方 API/Raw，或已固定的未过期指针。
- 下载按用户要求接入 MUDL-C，最多 16 个来源、32 个连接。预解析跳转必须为 HTTPS；原生引擎仍会处理后续重定向，最终内容信任由官方摘要与独立整包校验建立。
- 本次不启用强制更新，策略边界为 0；支持未来经版本控制显式调整。

## 版本与源

程序集 `NICRoute.dll` 内包含 `NICRoute.AppId`、`NICRoute.VersionCode`、`NICRoute.VersionName`、`NICRoute.Platform` 元数据。所有新旧判断只比较 `VersionCode`；名字用于展示并与 Release 标签/实际 PE 版本核对。

`updates/{stable|beta}/latest.json` 是权威指针。其清单路径包含策略 revision 和清单 SHA256。清单包含安装包 SHA256、大小、版本、渠道、更新内容及经过发布时校验的 HTTPS 下载地址。

客户端持久化已接受的最高 revision、指针摘要和强制边界。旧 revision、相同 revision 的不同内容、降低已知强制边界均拒绝。检查及清单响应不超过 1 MiB，请求有超时、cache-buster 和 no-cache。每个渠道分别保存信任状态。

镜像不具有策略权限。即使镜像返回正确的文件大小、样本或 HTTP 200，仍必须通过官方 SHA256；下载成功的旧状态不能替代安装前重新计算哈希。无发行方签名的首个版本依赖 GitHub 官方 HTTPS 和仓库权限，不能宣称已实现发行方密码学签名。签名版本更新时要求系统 WinVerifyTrust 成功且证书摘要连续。

## 安装

1. MUDL 下载到按版本代码和 SHA256 隔离的 `.download` 文件，原生校验后客户端再次独立计算整包 SHA256，原子改名为 ZIP。
2. 在新建会话目录展开包，拒绝路径穿越、绝对路径、设备名、大小超限、重复路径、符号链接和文件清单外内容；逐文件校验 SHA256。
3. 检查真实 PE 身份和版本，检查已有签名连续性，保存规则。停止引擎，启动暂存目录内的更新辅助进程，再退出主程序。
4. 辅助进程校验父进程 PID 与开始时间并等待退出，不强行终止其他同名进程。再次从 ZIP 校验/展开可信负载，备份所有将被修改的文件。
5. 只替换新旧包清单管理的文件。LocalAppData 配置和用户添加的文件保留。写入异常时按备份回滚。
6. 新程序启动后写会话确认；未能启动或超时则停止本次启动的进程并回滚，再尝试重启旧版。日志和备份保留在会话目录。

失败回滚是正常异常恢复，不是断电事务。其他进程占用、磁盘损坏或备份恢复失败时仍可能需要手动恢复。不能把更新过程当作断网隔离；更新期间引擎停机，恢复系统路由。

## 发版

1. 更新 App 项目的 `Version` 和单调递增的 `AppVersionCode`。
2. 在 `updates/policy.json` 中显式递增目标渠道 `policyRevision`；保留/审核 `maxForcedVersionCode` 并填写原因。不要手工改生成的 latest 或清单。修改任意清单内容（包括源列表）都要新 revision。
3. 编写 `docs/releases/vX.Y.Z.md`，提交并推送。
4. 手动触发 `Publish release`，提供标签和完整源提交 SHA。工作流构建该提交，运行策略、分流、MUDL 和更新进程测试，再发布唯一 Windows ZIP、源码和 SHA256SUMS。
5. Release 公开且附件可下载后，读取 ZIP 内的实际 PE 身份。候选镜像匿名下载全部文件并核对大小和 SHA256；仅通过的源进入清单。
6. 将不可变清单和 latest 指针放在同一 Git tree/commit，以非强制快进更新 main；并发更新失败则重新读取，不覆盖其他提交。镜像全部失败不阻止已验证的官方源；官方源不可用则不更新清单。

工作流 `contents: write` 已由用户持续授权；令牌仅来自 GitHub Actions 上下文，不写入发布包、客户端或镜像请求。所有发布串行，旧资产不会被新字节覆盖；重跑会重新验证并复用同一发布中已存在的完整资产。

## 验证

策略测试覆盖共享会话、手动绕过缓存/跳过、版本代码、渠道、强制边界、冲突/回滚、官方失败时的固定清单、损坏下载和逐文件校验。

`scripts/Verify-Updater.ps1` 构造两套独立运行的无界面替身，在临时目录运行真实更新辅助程序；分别验证新版本启动成功及故意启动失败后的旧版回滚、重启和配置保留。它不会安装到实际 NICRoute 目录。

工作流还启动正式 WPF 包导出预览，防止辅助程序运行时覆盖 WPF 程序集等仅在完整包中出现的问题。
